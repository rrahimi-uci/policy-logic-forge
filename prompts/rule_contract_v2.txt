# Non-overridable Structured Rule Contract v2

This contract is appended by agent_03 after the active domain prompt. It controls the
shape of every extracted rule. Domain prompts may add terminology and examples,
but must not change these field names, types, or validation rules.

Return JSON using the container requested by the active prompt. Every rule in that
container MUST use this structure:

Rules:

1. Each condition predicate is exactly one comparison for one variable. Never
   copy a prose condition into multiple values.
2. Use a nested tree for mixed logic such as A AND (B OR C):
   `{"all": [{"predicate_ref": "p1"}, {"any": [{"predicate_ref": "p2"}, {"predicate_ref": "p3"}]}]}`.
   When the quoted source states a genuinely unconditional obligation, use an
   empty `condition_predicates` array, `{"constant": true}` condition logic,
   and `condition_basis: "unconditional_explicit_in_source"`. Never use this
   shape merely because extraction failed to identify a condition.
3. Declare every predicate and outcome variable in `variables`. Use `string`
   only for genuine free text and add `"free_text": true`; use `enum` plus
   `allowed_values` for categories. Use `time` only for ISO local-time values
   such as `21:00`; use `date_time` for an ISO timestamp with a date.
4. `responsible_party` and `counterparties` must use an existing entity whose
   `concept_kind` is `actor_role`. A loan, property, document, report, process,
   decision variable, or other business object is never a party merely because
   the rule concerns it. The source must name or unambiguously identify every
   party, and non-empty counterparties require dedicated field evidence.
5. At candidate extraction, use `exception_basis:
   "not_found_in_chunk_recheck_needed"` whenever the provided chunk cannot
   establish the exception result. agent_07 must later replace it through a
   complete organized-source-document recheck. Final output may use only
   `explicit_in_source`, `explicitly_none_in_source`,
   `no_exception_cue_found_in_complete_search`, or a specifically explained
   unresolved final state; the candidate state is forbidden. The no-cue state
   requires the complete searched chunk count and corpus digest and must not be
   described as an explicit statement in the source.
6. `scope_basis: "explicitly_universal_in_source"` requires direct universal
   source wording. Do not infer universal scope from silence.
7. Every test vector must be source-attested or derived from the source. Numeric
   rules need a `boundary_condition: true` vector at a stated threshold.
8. `source_reference.source_text` and every `field_evidence` quote must be
   direct source text from the provided input, never a paraphrase.
9. If a value is absent or ambiguous, keep the rule but mark
   `requires_review: true` and state the uncertainty in `review_reason`.
10. `inferred` scope with all scope dimensions empty is a candidate only. The
    final readiness stage must use direct scope evidence, explicitly universal
    language, genuinely_unscoped after source review, or an explained
    unresolved state.
11. Every populated `applicability_scope` value requires dedicated
    `field_evidence.applicability_scope`. Chapter context, dataset topic, and a
    generic product word do not establish a narrower scope.
12. An exception is a source-stated input circumstance that changes, waives,
    or carves out the rule. Never encode the rule's own output variable, the
    opposite of its outcome, or an ordinary condition as an exception. An
    exception variable must have role `input` or `derived`, never `output`.
    When an exception assigns alternate consequences, extract that branch as a
    separate rule whose ordinary conditions are the exception circumstances;
    do not place alternate outcome assignments inside `exceptions`.
13. `workflow_semantics` is optional and normally null. Populate it only when
    the source directly states a prescriptive trigger and ordered process. Its
    shape is `{"kind":"prescriptive_process","basis":"explicit_in_source",
    "trigger_event":"...","actor_role":"EXISTING_ENTITY_TYPE_ID",
    "ordered_steps":[{"step_id":"s1","name":"...","kind":"user_task |
    service_task | business_rule_task | send_task | receive_task"}],
    "evidence":[{"chunk_path":"...","section_id":"...","source_text":
    "direct quote proving the order"}]}`. Use at least two ordered steps. Never
    infer an order from graph dependencies or from a party plus an outcome.
