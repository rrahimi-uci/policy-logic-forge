DECIDE, FOR EACH ATTRIBUTE

1. `owner` — which class the attribute describes. Ask what real-world thing
   holds this value, not who is responsible for checking it. A lender does not
   own a loan's ratio; the loan does. Use an existing class name from the list
   above when one fits.

2. `new_class` — set this instead of `owner` only when the attribute clearly
   describes a business entity that is missing from the list, and at least two
   other attributes in this batch belong to it. A class holding one attribute
   is not a class; leave that attribute unowned instead.

3. `value_object` — a name, when the attribute is one component of a composite
   value that has no identity of its own and is always handled as a unit
   (an address, a money-with-currency pair, a date range). Give every component
   the same `value_object` name so they group. Leave null when the attribute
   stands alone.

4. `confidence` — "clear" when the attribute's own wording settles it,
   "probable" when it follows from context, "unclear" when it genuinely could
   belong to more than one class.

Return `owner: null` and `confidence: "unclear"` for anything you cannot place
on the evidence shown. That is a correct, useful answer. Guessing is not: an
attribute on the wrong class silently corrupts the model, while an unplaced one
is simply reviewed. Never place an attribute merely to avoid leaving it empty.

RULES THAT CONSTRAIN THE MODEL

- Do not create a class for a rule, a check, a requirement, or a decision. Those
  are behaviour. Classes are the things behaviour is about.
- Do not create a class whose attributes are all booleans recording whether some
  rule passed. Those are outcomes of evaluation, not business state.
- Prefer fewer, well-populated classes over many thin ones.
- Two attributes describing the same fact under different names belong to the
  same class; say so via `synonym_of` naming the other symbol.
