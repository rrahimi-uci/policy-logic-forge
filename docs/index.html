Policy Logic Forge turns compliance policy text into a typed, source-grounded knowledge graph — every rule independently verified against the source document, not just cited. It separates "does this point to a source," "is each claim supported," and "is this rule safe to auto-execute" into three different, honestly reported numbers instead of collapsing them into one.

The problem

One quality number usually hides three different questions

On a real 1,191-page mortgage policy guide, 522 of 628 extracted rules — 83.1% — landed on a quality hold. Read on its own, that looks like a system that mostly doesn't work. It isn't; it's a single number standing in for questions that need separate answers.

📎

Does it point to a source?

Every rule needs a citation — but a citation isn't proof the claim it supports is actually true.

✅

Is each claim supported?

A claim-by-claim check, independent of extraction, against the real corpus text — not the model's memory of it.

🔒

Is the whole rule safe to execute?

Strict, whole-rule certification is a much higher bar than any single supported claim — and the two get conflated constantly.

How it works

Twelve agents, one continuous evidence spine

Source passage → concept → rule → decision or process model — and back again: model element → rule → claim → the exact passage that supports it. Every stage writes its own checkpointed artifacts; nothing downstream trusts an upstream claim without its own verification pass.

01Organize documents 02Extract entities 03Extract rules 04Validate 05Merge 06Optimize + dedupe 07Readiness gate 08Remediate 09Ground independently 10Dependency DAGs 11DMN · BPMN · CMMN · SBVR 12Knowledge report

Stage 09 (Grounding Verifier) is deliberately independent of extraction: it rebuilds evidence from the raw corpus itself rather than trusting a stored citation. A hallucinated citation cannot pass. See the full execution flow in ARCHITECTURE.md.

Real results, decomposed honestly

The same run, reported as five separate signals

This is the actual snapshot from the 628-rule mortgage run that produced the 83.1% headline number above — broken into the questions that number was quietly averaging together.

  • 100%of rules had a source pointer
  • 91.9%of individual grounding claims were supported
  • 17.7%of complete rules passed strict whole-rule grounding certification
  • 13.1%of rules required actual human judgment
  • 83.1%remained on an automated quality hold — a fail-closed default, not a failure report
Independent verification

The system is built to catch its own mistakes

A deterministic guard checks whether two rules in a claimed dependency share any variable name at all — deliberately weak, catching only the clearest false positives. It exists because it isn't the last line of defense: independent grounding verification is.

On a real mortgage-domain run, that independent pass — agent_09, run separately from extraction — found that a large share of claimed dependency/conflict relationships did not actually hold up once checked structurally, despite having already passed the pipeline's own deterministic guard.

44%of dependency/conflict claims did not
hold up under independent verification

Every model verdict of supported/contradicted is downgraded to insufficient evidence unless the cited quote resolves to a genuine substring of the real corpus text — a hallucinated citation cannot pass, even if the model insists it's supported.

Real standards output

DMN, BPMN, CMMN, and SBVR — generated, not approximated

Every run emits real, standards-conformant artifacts grounded in the certified graph — reviewable by a business analyst, importable into a real decision-modeling tool, not a bespoke JSON shape invented for this project.

DMN 1.3

One decision table per rule — real input/output columns and a FEEL-expressed rule row, not a diagram approximation.

BPMN 2.0

Generated only where a rule has an explicit, source-evidenced trigger, actor, and at least two ordered steps. A party plus an outcome is not a process — sometimes the most accurate diagram is no diagram.

CMMN 1.1

Review-and-remediation cases for anything routed to human judgment or case management, with a real task and milestone structure.

SBVR

A governed business vocabulary kept honestly separate from executable decision variables — one run: 26 governed concepts alongside 3,148 rule-local decision variables, not the same number wearing two names.

Also included

RegDelta — know exactly what changed between two policy versions

A differential-execution engine layered on top of the pipeline: compile two versions of a policy to a shared intermediate representation, align their rules, classify what semantically changed, and propagate the impact through the dependency graph — so a policy update tells you which downstream rules and cases actually need re-review, not just that something changed.
